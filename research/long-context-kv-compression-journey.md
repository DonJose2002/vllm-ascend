# 长序列 KV 压缩复盘(人话版,给同事)

> 2026-09-15 整理。技术细节版见 `long-context-kv-compression.md`(同目录);
> 实验设计/判读在笔记仓 `experiments/phase2-*.md`。
> 一句话:先在别人的方案(hamming)上量出三本账,再用自己的方案(静态真释放 +
> 注意力投票)把三本账全部立正——中间顺带把"vllm 编译后的模型里 python 去哪了"
> 这个问题排了五轮障。

## 0. 问题:每写一个字,都要把满书房的书重读一遍

模型生成每个 token,都要重读这个请求的全部历史 KV。16K token 的提示词,
就是每写一个字先读 16K 字的"书房"。书房带来三本账:

- **书架钱(显存)**:书线性增多,书架要越来越大;
- **读书时间(带宽)**:ITL(每个字的耗时)斜率就是读 KV 的价签——实测 4K
  上下文每步读 16.6GB(≈11ms),32K 读 89GB(≈60ms);
- **读漏的风险(质量)**:任何"少读点"的压缩方案,都可能把要用的那本漏掉。

Phase 2 的任务:把"少读点"落到昇腾引擎,三本账一起量。

## 1. 方案一(别人的):hamming_sparse —— 每步都重新挑书的勤奋管理员

vllm-ascend 内置的方案,思路很巧:**不动读书的规矩,只每步换一张书单**。

- 入库时(prefill):给每本书(每个 token 的 key)用随机投影算一个 128bit
  "内容指纹"贴上;
- 读书时(decode 每一步):拿当前问题(query)也算指纹,跟全书房比对**海明
  距离**,挑最相近的 4096 本(默认),外加"第一本"和"最近几本"保底;
- 然后把书单(block_table)和"要读的长度"(seq_lens)一改,FIA 算子照读
  ——它根本不知道自己读的是删减版。

免训练、查询感知、每步都按当前问题重新挑——理论上很漂亮。我们把它当基线
跑了一个 12+2 cell 的矩阵,三本账量出来是:

### 书架钱:一分没省

被"淘汰"的书**并不下架**,还在书架上占着位置(代码里没有任何 free/evict),
指纹库还倒贴 0.4%。它是省读书时间的方案,不是省书架的方案。

### 读书时间:收益被地板吃了,还倒贴加班费

两个原因叠加:

1. **它上不了流水线(图不兼容)**:每步都改书单,导致计算图没法固化捕获,
   一捕获就越界崩。只能跑 eager(逐步解释执行)。而 eager 有个 ~72ms 的
   "host 地板"——每步光准备工作就要 72ms,**省下来的读书时间(几 ms 量级)
   全淹在地板下面,物理上根本测不到**。
2. **它自己还要收加班费**:每层每步重选一次(36 层 × 每层 7-9 次算子发射)
   加每步一次同步,**常数 +17~24ms**,与压缩强度、上下文、并发全无关。

另外把旋钮拧过头会直接死:topk 开到 8192(64 chunk)越过了算子测试覆盖
边界,引擎直接死亡(判死,不追——上游已把这个特性整体移除了)。

### 读漏风险:预算 4K 以上是满分,但摸到一条下限

topk4096(16K 保留 26%、32K 保留 13%)NIAH 大海捞针**满分**;但同为 13%
保留率,绝对量 2048 本就掉到 0.9 分,32K 下(只剩 6.6%)塌到 0.2。
**结论:质量不看比例看绝对量,预算下限 ~4K 条。**

### 附带收获:一个静默开关的实锤

hamming 和投机解码(SD)是互斥的,而且是**静默**关闭(代码里一个
`and not speculative_config`,连警告都没有)。我们用行为数据实锤了:
同开时它的行为逐位等于"hamming 根本没开"。这是 Phase 4 要打破的墙。

**裁决:hamming 被证伪的不是精度(动态选择满分),是工程形态**——每步重挑
这个"动态"属性,就是 host 税 + 图不兼容 + 收益被地板吃掉三宗罪的共同根源。
所以我们自己的方案定案为:**静态、一次性、真下架**。

## 2. 方案二(我们的):static_kv_compact —— 读完序章,一次性断舍离

核心思想(SnapKV 正统形态):**一个请求读完序章(prefill 结束)的那一刻,
一次性决定哪些书这辈子都不会再看,直接扔出书房;之后整个写作过程(decode)
只读留下的书**。

对比 hamming:一次性(之后零成本)vs 每步重挑;书真扔(书架钱也省)vs 一本
不扔;选书策略可以换(机制和策略解耦)vs 绑死指纹那套基建。

### 扔书这件事,比想象中讲究

引擎里"书的位置"被七八处记账同时引用,直接抽走会全乱。两个关键手法:

1. **null 保位**:扔掉的书留一个"空位牌"(null block)在原位,所有按位置
   算账的逻辑(追加/准入/增长)照常运转;同时把空位物理归还书架池,别人
   立刻能用——**账面不动,物理真释放**;
2. **视图 gather**:引擎内部的"书架行"原样保留(动了会写错槽位),只在每次
   读书前,按新书单把要读的书 gather 成一张紧凑视图递给算子;算子看到的
   长度也相应变短。**没开压缩的请求走原路,一个字节都不变(零开销)**。

安全起见上了六道门禁:单卡同进程、关 async 调度、关 SD、关前缀缓存……
任何一条不满足就静默不压(后来证明这些门禁都救过场)。

### 效果:机制三验证全过

图模式(PIECEWISE+FULL 各 35 张图)全程无崩;16K 请求释放 91/123 块、
32K 释放 210/247 块,用量曲线肉眼可见地"prefill 后 5.5% → 压缩后 1.5%
→ 结束 0%";视图确实被装上了(下面的质量事故就是证据)。

## 3. 选书策略的两代:从"闭眼等距抽"到"让作者试读"

### 第一代 stride:闭眼等距抽 —— 机制跑通了,质量判死

第一版刻意选了个最保守的策略:留第一本、留最近四本,剩下按等间隔抽。
结果 NIAH 只有 0.20——正好是保留率的数学期望(16K 保留 26%、32K 15%,
捞针命中率 ≈ 抽奖概率)。**这不是 bug,是闭眼抽的必然**;它反过来证明了
"每步动态重选"才是 hamming 满分的原因,这个性质不遗传给任何静态方案。
选书策略升级成主矛盾。

### 第二代 dwvote:让作者试读几页,看他老翻哪几页

思路:想知道哪些书重要,**最权威的信号是模型自己的注意力**。让请求生成
头 8 个 token 时,把每一步的"真实问题"(query)在每一层和全书房算一遍
注意力,统计每本书被"翻"的强度,按强度留下前 4096 本。

对捞针任务这简直是开卷考试:模型要报出密码时,头几个字一定会猛翻写着
密码的那页——那页书以全票留下。

**效果(run 10,全绿)**:19 次压缩全部走投票、零兜底;**NIAH 满分**
(对比 stride 的 0.20);**ITL 19.6ms 还比不压缩的 21.6ms 快 2ms**(读的书
少了,物理可见);书架释放如前。代价是那头 8 步要切回 eager"试读"
(延迟尾巴 itl99 110ms)——净收益 = 读书省下的 − 试读开销,待全矩阵量化。

## 4. 番外:让"作者试读"这件事,排了五轮障

dwvote 的实现原理只需一句话:在头 8 步跑 python 前向,让 hook 触发。
**但在 vllm 编译后的模型里,"跑 python 前向"这个要求意外困难**——run 5-9
五连挂,根因各不相同,构成一条"编译包裹链":

1. **run 5**:图模式下 attention 被编进编译区,hook 挂在 python 模块上,
   而 replay 根本不经过 python——钩子是有的,永远没人按;
2. **run 6**:那就强制 eager——`torch.compiler.disable()` 一包,引擎直接死
   (torch 2.6+ 禁止把它当上下文管理器用,一进入就抛异常);
3. **run 7**:换官方 stance API——无效。vllm 给模型基类里混进了一个
   `__call__` 永远派发编译产物的 wrapper,stance 到不了 python;
4. **run 8**:绕过 `__call__` 直调 `.forward`——还是零投票,但不报错;
5. **run 9**(四角探针定位):前向确实"跑完"了(62ms),但 36 层 hook 一个
   没响。真相:**编译装饰器挂在内层 Qwen3Model 上,不在外壳上**——我们调的
   外壳 forward 确实是纯 python,但它函数体第一句 `self.model(...)` 就撞进了
   内层的编译派发,36 层还是被压平在编译产物里。修复:再下沉一层,直调
   内层模型的原始 `.forward`;顺手拆了第二颗雷(Qwen3 用关键字参数调
   attention,hook 按位置参数读会当场炸)。

教训:在编译过的引擎里,"看起来 eager 的步"和"真的在跑 python"是两回事;
每个修复必须自带自证日志,一次定位一环。

## 5. 三本账总对比

| | hamming(别人的) | static_kv_compact + dwvote(我们的) |
|---|---|---|
| 挑书方式 | 每步按当前问题重挑 | 序章读完一次性定,作者试读投票 |
| 书架钱(显存) | 一分没省(还倒贴) | 16K 释放 74%、32K 释放 85% 的块 |
| 读书时间 | 收益测不到,倒贴 +17~24ms 常数税 | **−2.0ms 已可见**,上限在 32K×高并发角落 |
| 读漏风险 | 预算 ≥4K 满分 | 满分(vs 闭眼抽 0.20) |
| 流水线(图) | 上不了 | 全绿 |
