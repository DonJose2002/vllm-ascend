# 给同事的复盘:eagle3 在长文档上"熄火"的真相(人话版)

> 2026-08-24 | 技术细节版见 `bugfix-eagle-h2d-race.md`(同目录)| 修复已在我们研究线验证并推了上游 PR 分支

## 故事版:发生了什么

我们给 Qwen3-8B 装了个"速记员"(eagle3 投机头,一个 1 层小模型):主模型每次动笔前,速记员先一口气猜 5 个词,主模型一次性核对,猜对几个就白赚几个——4K 短文档上效果拔群,每个词的成本降了一半多。

然后我们喂了一份 16K 的长文档。**引擎当场死亡**,报错是一串看不懂的硬件码(EZ9999,vector core exception)。更气人的是:同样的代码,4K 偶尔死、16K 必死、换三张卡都死、关各种功能都死。

## 悬念三连

**问:是不是模型权重坏了?**

不是。权重坏了应该 4K 也吐乱码,而它 4K 表现完美。而且三张不同的卡都崩——硬件背锅也排除了。

**问:那到底死在哪?**

昇腾有个"事故黑匣子"(plog 日志),里面记了真正出事的算子:一个**查词表的 gather**,它的输入里混进了一个魔法值 `0xa5a5a5a5`——这是 CANN 给"从没写过的新内存"涂的记号。翻译成人话:**有人拿着一张没填完的表格去查字典,把页码当成了词**,一查就查到了地图外,芯片当场自我保护停机。

**问:表格是谁没填完?为什么只有长文档出事?**

这是整个案子最漂亮的一步。每步解码前,系统会把一小批"兜底词编号"从内存(CPU)拷到卡上(NPU)。这份拷贝用的是**非阻塞模式**——相当于快递寄出就走人,不等签收。

在英伟达卡上,这个"不等"是安全的:显卡的规则保证"同一队列里,先寄的快递一定先被拆"。**昇腾的这条规则没写全**:这种小拷贝走的是一个独立的小车(SDMA 搬运引擎),小车和主力车队(计算流)**谁先到,规则没承诺**——注意不是"必然乱序",而是"没保证顺序"。多数时候小车还是先到的,所以短文档全绿;一旦没到,就是这次的事故。

于是:长文档 → 队列里排满了活 → 小车在路上被堵 → 下游"查词表"的工人先到了,拆开包裹一看,里面还是出厂时的涂鸦(0xa5a5)→ 炸。

短文档队列浅,小车大概率赶在工人前头,所以只是偶尔翻车。

## 你可能会追问的

**上游 vllm 在 GPU 上跑同样的代码,凭什么没事?**

代码一模一样,但 GPU 的流(stream)语义承诺了顺序,昇腾这边没有。这不是谁的代码写错了,是**"在 A 平台安全"的写法搬到 B 平台需要重新审**——CUDA 的直觉不能白嫖。

**为什么 draft_model 和 dflash(另外两个速记方案)没事?**

严格说:**它们不是没事,是没爆过**。这条有问题的拷贝是四类速记方案里的三类共享的(eagle 系、draft_model、dflash 都要走),垃圾同样可能混进它们的输入——区别在于下游:它们拿到"兜底词编号"后先过一道专用搬运算子、再跑一个更重的头模型(0.6B 或 5 层),消费链长、窗口宽,所以我们的几十组测试一次都没翻车。但**没翻车不等于没坐在危险的位置上**——这次修复把拷贝本身修好,等于同时拆掉了它们脚下同一条雷管。

真正和这条拷贝无关的只有 ngram(查字典型速记):它在 CPU 上翻 prompt 找重复段,根本不下设备,从头到尾碰不到这个 buffer。

**dflash 呢?**

见上一问——dflash 属于"共享毒源、消费链不同、实测未爆"的一类,不是免疫。

**怎么确认就是这条拷贝?**

做了个"不影响时序的二分实验":在嫌疑数据进速记员之前,偷偷把越界的编号**钳回合法范围**(一次极轻的运算,不改变任何时间关系)。只钳"兜底词编号"这一路 → 不崩了;只钳另一路 → 照崩。铁证:垃圾就在"兜底词编号"的拷贝路上。

另外还有个杀手锏:`ASCEND_LAUNCH_BLOCKING=1`(让每个任务都"签字画押再走")一开就不崩——**能被"强制同步"治好的病,病根必然是竞态**。这个环境变量是查这类病的活化石工具,但记住:**只能用来诊断,不能用来治病**(性能不可接受,而且它治好的只是表象)。

## 修复是什么?一句话

把这条拷贝从"非阻塞"改成"阻塞"。它只有几百字节,等一下的成本是微秒级,换一个确定性的顺序,血赚。

## 值得带走的三句话

1. **昇腾上看到 0xa5a5a5a5,就是"读了没写过的内存"**,顺着"谁还没写完就被读"找,八成是异步问题;
2. **崩溃报错的位置不是案发位置**(异步世界的报案永远迟到),先看 plog 里 fault kernel 是谁;
3. **"偶尔失败"比"必现失败"更危险**:这次 4K 的偶发空流,和 16K 的必死,是同一个凶手——偶发问题按必现问题查,别放过。
