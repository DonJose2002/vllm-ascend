# 给同事的复盘:eagle3 在长文档上"熄火"的真相(人话版)

> 2026-08-24 初稿,2026-08-25 补判别实验续集与终判 | 技术细节版见 `bugfix-eagle-h2d-race.md`(同目录)| 修复已在我们研究线验证并推了上游 PR 分支

## 故事版:发生了什么

我们给 Qwen3-8B 装了个"速记员"(eagle3 投机头,一个 1 层小模型):主模型每次动笔前,速记员先一口气猜 5 个词,主模型一次性核对,猜对几个就白赚几个——4K 短文档上效果拔群,每个词的成本降了一半多。

然后我们喂了一份 16K 的长文档。**引擎当场死亡**,报错是一串看不懂的硬件码(EZ9999,vector core exception)。更气人的是:同样的代码,4K 偶尔死、16K 必死、换三张卡都死、关各种功能都死。

## 悬念三连

**问:是不是模型权重坏了?**

不是。权重坏了应该 4K 也吐乱码,而它 4K 表现完美。而且三张不同的卡都崩——硬件背锅也排除了。

**问:那到底死在哪?**

昇腾有个"事故黑匣子"(plog 日志),里面记了真正出事的算子:一个**查词表的 gather**,故障参数里混着魔法值 `0xa5a5a5a5`——这是 CANN 给"从没写过的新内存"涂的记号。翻译成人话:**有人拿着一张没填完的表格去查字典,把页码当成了词**,一查就查到了地图外,芯片当场自我保护停机。

(后记:0xa5a5 是这次破案最初的路标,但**最终定谳的逃逸值其实不是它**——是表格里的一个旧占位符 `-1`,详见下面"续集"。0xa5a5 出现在黑匣子的另一个字段里,当时把我们指向了"未初始化内存"的方向,方向对,角色错。)

**问:表格是谁没填完?为什么只有长文档出事?**

这是整个案子最漂亮的一步。每步解码前,系统会把一小批"兜底词编号"从内存(CPU)拷到卡上(NPU)。这份拷贝用的是**非阻塞模式**——相当于快递寄出就走人,不等签收。

在英伟达卡上,这个"不等"是安全的:显卡的规则保证"同一队列里,先寄的快递一定先被拆"。**昇腾的这条规则没写全**:这种小拷贝走的是一个独立的小车(SDMA 搬运引擎),小车和主力车队(计算流)**谁先到,规则没承诺**——注意不是"必然乱序",而是"没保证顺序"。多数时候小车还是先到的,所以短文档全绿;一旦没到,就是这次的事故。

于是:长文档 → 队列里排满了活 → 快递在路上被堵 → 下游工人先到,拆开包裹一看,里面是**这格上一次的旧值**(定谳:一个本不该被消费的占位符 -1,见续集)→ 拿去查词表 → 炸。

短文档队列浅,快递大概率赶在工人前头,所以只是偶尔翻车。(后来实测发现这份负载下逃逸点固定在同一步——"偶尔"其实是"每一步掷一次骰子,掷够次数必中",详见续集末尾。)

## 你可能会追问的

**上游 vllm 在 GPU 上跑同样的代码,凭什么没事?**

代码一模一样,但 GPU 的流(stream)语义承诺了顺序,昇腾这边没有。这不是谁的代码写错了,是**"在 A 平台安全"的写法搬到 B 平台需要重新审**——CUDA 的直觉不能白嫖。

**为什么 draft_model 和 dflash(另外两个速记方案)没事?**

严格说:**它们不是没事,是没爆过**。这条有问题的拷贝是四类速记方案里的三类共享的(eagle 系、draft_model、dflash 都要走),出事的"门"(下面续集会讲)三方案一模一样——区别在**单位时间掷骰子的次数**:eagle 头每步是微秒级的密集发射,把 host 推得很靠前、窗口更宽;draft_model/dflash 每步是毫秒级的大动作,同样时长里掷骰子的次数少得多。**没爆过不等于没坐在危险的位置上**——这次修复把拷贝本身修好,等于同时拆掉了它们脚下同一条雷管。

真正和这条拷贝无关的只有 ngram(查字典型速记):它在 CPU 上翻 prompt 找重复段,根本不下设备,从头到尾碰不到这个 buffer。

**dflash 呢?**

见上一问——dflash 属于"共享毒源、实测未爆"的一类,不是免疫。(旧版解释"消费链长所以窗口宽"已被我们自己的推演推翻:值传播跟链长没关系,链长也影响不了首读时序——技术版 §3.2 有完整论证。)

**怎么确认就是这条拷贝?**

做了个"不影响时序的二分实验":在嫌疑数据进速记员之前,偷偷把越界的编号**钳回合法范围**(一次极轻的运算,不改变任何时间关系)。只钳"兜底词编号"这一路 → 不崩了;只钳另一路 → 照崩。当时读作"铁证:垃圾在这条路上"。**续集会修正这个读法**:钳子救活靠的是"值消毒",不是"当了路障"——但它确实把嫌疑范围钉死在了这条路上,这个贡献不变。

另外还有个杀手锏:`ASCEND_LAUNCH_BLOCKING=1`(让每个任务都"签字画押再走")一开就不崩——**能被"强制同步"治好的病,病根必然是竞态**。这个环境变量是查这类病的活化石工具,但记住:**只能用来诊断,不能用来治病**(性能不可接受,而且它治好的只是表象)。

## 修复是什么?一句话

把这条拷贝从"非阻塞"改成"阻塞"。它只有几百字节,等一下的成本是微秒级,换一个确定性的顺序,血赚。

## 续集(2026-08-25):凶手到底带了什么值

修复上线、9/9 全绿之后,案子其实还剩一个没闭合的问题:**竞态窗口里读到的"垃圾",到底是什么?** 我们自己推演出一堆矛盾:那个 buffer 是开机就清零的常驻表格,按理说读到的应该是零或旧值,都是合法编号,炸不了——除非快递撕碎了落地(把出厂涂鸦 0xa5a5 写进表格),可这又解释不了为什么必现。两个候选故事:**"值故事"**(垃圾真在值里)vs **"屏障故事"**(乱序的是别的一对,修复只是碰巧当了路障)。

**仪器:三个"只数数、不碰值"的计数器。** 在三个关键位置各装一个数数器(全程在卡上数,零同步,不惊动任何时序):拷贝后数表格里的非法编号(c1)、"门"开了几次(c2)、非法编号流出去了几个(c3)。再配两个开关:一个能把修好的拷贝**复活回竞态状态**(不然观察不到病),一个管计数器开关。**还有一个保活钳**:复活竞态必崩,崩了计数器就读不回来——所以同时开 clamp 钳子保命,而钳子在计数器**之后**才动手,不影响读数。

破案路上还顺手踩了两个坑,都值得记:

- **Run 1 的意外信息**:只复活+计数(无钳)→ 照崩。这本身是重要证据:计数的小运算和 clamp 钳子插在同一位置、同类运算,**钳子能救命而计数不能**——说明钳子救命靠的是"消毒"不是"路障"。屏障故事从这里开始塌。
- **读数差点全丢**:进程正常退出时,两个"临终读数"机制(atexit/析构)一个都没触发——vllm 引擎的退出路径绕过了它们。解法:**给进程装个"随时喊话"的信号钩子**(SIGUSR1),引擎活着的时候任何时候 `kill -USR1` 一下,计数器当场吐数。后来还让跑分脚本在收摊前自动喊一嗓子。**教训:别把读数押在"进程怎么死"上。**

**Run 2' 的读数**(843 步,复活+计数+保活钳,绿跑):

> 门开 7 次,逃逸 1 个非法编号(c3=1)。

门开 7 次里 1 次读到没落地旧值——**这 1 个逃逸就是无钳版本里那场引擎死亡**。值故事坐实一半。

**Run 3 的意外 → 全案最大反转。** 按值故事预测:关掉复活(修复生效、拷贝落地),表格应该干净,c1 应归零。结果:**c1 = 840/847,还是 99%**。去查上游源码,真相令人哭笑不得:那张"兜底表格"平时填的本来就是 **-1(占位符)**——上游约定"还没写进正式答案的位置,兜底值就是 -1",而且这些行正常情况下**永远不会被消费**(门关着)。所以 c1 数出来的 99% 全是这个合法的占位符,不是垃圾。数字上有个铁证:`847 - 840 = 7`,恰好等于门开的次数(门开的行填的才是真词)——两次实验完美重合,不是巧合是算术。

**Run 4 定谳。** 加了两个终极探针再跑:c1x(数"排除 -1 之外的真垃圾")和 esc(记下逃逸值的实际数字)。读数:

> c1x = 0,esc = **[-1, -1]**

逃逸出去的那个"垃圾",就是**上一轮落地的旧占位符 -1**。0xa5a5 从头到尾没进过值路径(黑匣子里那个是别的字段的记号)。

**最终版故事(全闭合):**

1. 平时每步,表格里躺着占位符 -1(设计如此,门关着,无害);
2. 偶尔(843 步里 7 次,都在请求收尾边界),门开了,host 赶紧往表格写真词,快递(非阻塞拷贝)在途;
3. 门开的瞬间工人来读,快递没到,读到**这格的旧值:-1**;
4. -1 被当词编号拿去查字典 → 查到字典外面 → 芯片停机。

修复(阻塞拷贝)= 快递必达后工人才读 → 门开必读真词 → 逃逸归零(实测 c3=0)。

还有个漂亮的收尾:两次同配置实验的计数器**逐位一模一样**(843/837/7/1)——这份负载下逃逸点固定在同一步。**"16K 必现"不是概率堆积,是确定性事件**;而"4K 偶发"是不同负载下逃逸点有时落在门关的步上,白读一次占位符但没人消费,无事发生。

## 还剩一个没钉死的问号(存档,不追了)

破案之后有个自然的追问:**三个速记方案共享同一条有病的拷贝,凭什么只有 eagle 翻车?** 我们推演到这一步停手,记录在案:

- **先排除一个直觉错误**:"eagle 的 kernel 快,所以抢跑"——不对,恰恰相反。快递(copy)和工人(where)各排各的队:工人队(计算队列)排得越长,工人来得越**晚**,快递反而越从容。所以"计算快"单独看是保护因子。eagle 必输的原因只能在**快递队(SDMA 搬运队列)排得更长**。
- **最强候选(未证)**:eagle 每步循环只有微秒级,同样的墙钟时间里它发射的步数远多于 draft_model/dflash(它们每步是几十上百毫秒的大活),快递队始终保持高压、消化不过来;到了门开的那步,兜底快递前面还压着一堆积压,输定了。而重 drafter 每步之间快递队有整段空闲被清空,门开那步快递几乎无人排队。
- **4K vs 16K 同理**:门开次数其实一样(都跟请求收尾走,~7 次),差别是门开那步快递队多深——16K 有 8 个 prefill 大块,每块带着一大票元数据搬运(随上下文变长的 block table),队被压深;4K 只有 2 块,队浅,快递基本都赶得上。
- 两条代码事实支撑这个框架:三个方案在"门开+快递输"之前的代码完全一样(差异必然全在窗口内),而且垃圾一旦逃逸对谁都是死刑(下游公共,无免疫可言)。

想钉死它需要给 SDMA 队列打点观测,以及给 4K 补一轮计数器——都记录在技术版 §3.4 的待验证清单里,暂不追。

## 值得带走的五句话

1. **昇腾上看到 0xa5a5a5a5,顺着"谁还没写完就被读"找,八成是异步问题**——但注意它可能只是路标不是凶手:这次真正的逃逸值是个旧占位符 -1,0xa5a5 出现在黑匣子别的字段里;
2. **崩溃报错的位置不是案发位置**(异步世界的报案永远迟到),先看 plog 里 fault kernel 是谁;
3. **"偶尔失败"比"必现失败"更危险**:这次 4K 的偶发空流,和 16K 的必死,是同一个凶手——偶发问题按必现问题查,别放过;
4. **"插个运算就治好"≠"时序问题在这里"**:钳子救活靠的是值消毒,不是当了路障——想定位值,用只数数不碰值的计数器;
5. **读数机制别押在"进程怎么死"上**:atexit 靠不住,活体信号(SIGUSR1)随时喊话才是稳的。
