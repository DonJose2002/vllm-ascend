# H2D 可见性竞态·人话版

> 技术版:`research/h2d-visibility-race-report.md`。这篇是给同事讲故事的版本:
> 不查代码,只用日常比喻,把"我们查了一整天、推翻自己七次"的过程讲清楚。

## 一、问题是什么(三十秒版)

程序把一个小数据(64 字节,像一张便利贴)从电脑内存拷到 NPU 的显存里,
用的是"异步拷贝、不用等"的方式。拷完之后,**同一条流水线上的下一个计算**
去读这块显存——**读到的却是上一轮的旧数据**。

就像你往快递柜里放了一件新包裹,系统显示"已投递",收件人马上去开柜——
拿到的是上一件。快递柜说:投递记录是真的,柜门顺序也没乱,但你的包裹
还在从货车到柜子的传送带上。

## 二、这不是什么(我们一开始全猜错了)

猜了一整天,以下七个答案**全被实验推翻**:

1. **"拷贝发错了流水线?"**——不是。档案(profile)显示拷贝工单就挂在
   正确的流水线上,和读它的计算任务同一条。
2. **"两个任务抢跑、并行执行了?"**——不是。档案显示它们严格一个做完
   一个才开始,顺序完全正确。
3. **"底层(CANN 库)的排队机坏了?"**——不是。我们绕开所有上层封装,
   直接调用最底层的拷贝接口,配上一模一样的积压压力:**只要读者也是
   拷贝通道(D2H),永远读到新数据**。
4. **"是 torch_npu 的中转队列捣乱?"**——不是。关掉队列照样乱(只要
   压力够);开着的队列只是把乱的概率放大到"几乎必然"。
5. **"换个线程提交就乱?"**——不是。我们用另一个线程按同样的次序提交,
   干干净净。
6. **"小拷贝走了另一条物理捷径?"**——不是。两条路的工单都在,大小
   拷贝走的是同一条 SDMA 通道。
7. **"拷贝后跟着的某个小查询其实是安全阀?"**——不是。把那个查询原样
   加回去,乱序率纹丝不动。

## 三、真相是什么

**货确实卸了,但还没进"计算车间看得见的仓库"。**

NPU 里有两种干活的车间:SDMA(搬运车间)和 AI core(计算车间)。
搬运工单完成后,货从搬运通道到"计算车间能读到的位置"之间,**存在一段
没人负责的最后一百米**。流(stream)这个排队系统只保证"搬运完成 →
计算启动"这个**顺序**,不保证"计算启动时货已经摆在它面前"。

这一百米走多久?看情况。所以这是一个**概率窗口**:

- 平时没什么积压:货总能赶在计算前面到 → 看起来一切正常(0% 出错);
- 稍微积压一点(前面排了 8 兆的大件):**一半时间出错**(47%);
- 积压一大(64 兆):**几乎必然出错**(99.94%);
- 官方提供的三种"等一下"的栅栏(事件等待/事件同步/整条流同步):
  **全都等不到这次拷贝**——因为排队系统眼里这个工单已经"完成"了,
  没有东西可等。

最气人的是:**"没错"和"必错"之间只隔着一个偶然**。我们有一组配置
平时 0% 出错,一度以为它安全——把压力加到 64 兆,99.94%。**0% 不是安全,
是还没轮到你。**

## 四、为什么只有 NPU 上炸、GPU 上没事?

同样的代码习惯(pinned 内存 + 异步拷贝 + 同一条流上接着算)在 CUDA 上是
教科书用法:CUDA 的流保证"前面的拷贝数据对后面的计算可见",这是白纸黑字
的语义。torch_npu 照抄了这套 API 的形状,但底下这条"最后一百米"没人修。
我们最初崩溃的那个引擎 bug(#14922),就是一张写着 -1 的旧便利贴被当成
新数据,送进了查词典的计算,一头撞出边界。

## 五、怎么办

- **立刻能用的安全写法**:拷贝时把 `non_blocking=True` 改成 `False`
  (同步拷贝)。我们的小数据只有 64 字节,同步的开销测不出来,线上已经
  这么修了(#14922)。
- **给华为报 issue**(下一步):材料已经备齐——不是报"哪里错了",而是报
  "这层语义缺了一块,请告诉我们正确的异步用法是什么"。
- **教训三条**:
  1. 测出 0% 错误不代表安全,可能是窗口没开;压力谱(从轻到重)才是体检;
  2. 监控本身会改变结果——我们一开性能档案,乱序就消失了(仪器把程序拖慢,
     货反而赶上了);
  3. "记录显示一切正常"和"数据真的到位"是两件事,**中间可能隔着一百米**。

## 六、一分钟年表

| 时间 | 发生了什么 |
|---|---|
| 08-24 | 修好线上崩溃(#14922 的前身),发现拷贝与消费之间没顺序保证 |
| 08-26/27 上午 | 做出最小复现:三级栅栏全部失效,一度定性"流外拷贝" |

| 傍晚 | 用户质疑"问题在底层"→ 我们绕开全部上层直接测底层:**底层反而没事**(读者换成拷贝通道后全绿) |
| 晚上前半 | 六种配置对照:关队列、换通道、加查询……数据互相打架,七个假说轮番上阵轮番阵亡 |
| 深夜 | 加压实验一锤定音:平时 0% 出错的配置,压力加大后 99.94% 出错——**没有安全的侥幸**,统一成"最后一百米"的窗口模型 |
