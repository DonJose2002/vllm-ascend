## 一、问题是什么(三十秒版)

程序把一个小数据(64 字节,像一张便利贴)从电脑内存拷到 NPU 的显存里,
用的是"异步拷贝、不用等"的方式。拷完之后,**同一条流水线上的下一个计算**
去读这块显存——**读到的却是上一轮的旧数据**。

就像你往快递柜里放了一件新包裹,系统显示"已投递",收件人马上去开柜——
拿到的是上一件。快递柜说:投递记录是真的,柜门顺序也没乱,但你的包裹
还在从货车到柜子的传送带上。

## 二、这不是什么(我们一开始全猜错了)

猜了一整天,以下七个答案**全被实验推翻**:

1. **"拷贝发错了流水线?"**——不是。档案(profile)显示拷贝工单就挂在
   正确的流水线上,和读它的计算任务同一条。
2. **"两个任务抢跑、并行执行了?"**——不是。档案显示它们严格一个做完
   一个才开始,顺序完全正确。
3. **"底层(CANN 库)的排队机坏了?"**——不是。我们绕开所有上层封装,
   直接调用最底层的拷贝接口,配上一模一样的积压压力:**只要读者也是
   拷贝通道(D2H),永远读到新数据**。
4. **"是 torch_npu 的中转队列捣乱?"**——不是。关掉队列照样乱(只要
   压力够);开着的队列只是把乱的概率放大到"几乎必然"。
5. **"换个线程提交就乱?"**——不是。我们用另一个线程按同样的次序提交,
   干干净净。
6. **"小拷贝走了另一条物理捷径?"**——不是。两条路的工单都在,大小
   拷贝走的是同一条 SDMA 通道。
7. **"拷贝后跟着的某个小查询其实是安全阀?"**——不是。把那个查询原样
   加回去,乱序率纹丝不动。

> 🪦 **2026-08-28 补第八块墓碑**:8. **"是可见性缺口(最后一百米)?"**
> ——也不是。这曾是本文的终判,三天后被我们自己的阴性对照推翻,
> 见文末续集。

## 三、真相是什么

> ❌ **2026-08-28:本节整体作废**——"读旧数据"从未在复现层发生过,
> 全部是"未来值"伪影;概率窗口(0%→47%→99.94%)是仪器伪影的谱系,
> 不是缺陷的谱系。原文保留如下。

**货确实卸了,但还没进"计算车间看得见的仓库"。**

NPU 里有两种干活的车间:SDMA(搬运车间)和 AI core(计算车间)。
搬运工单完成后,货从搬运通道到"计算车间能读到的位置"之间,**存在一段
没人负责的最后一百米**。流(stream)这个排队系统只保证"搬运完成 →
计算启动"这个**顺序**,不保证"计算启动时货已经摆在它面前"。

这一百米走多久?看情况。所以这是一个**概率窗口**:

- 平时没什么积压:货总能赶在计算前面到 → 看起来一切正常(0% 出错);
- 稍微积压一点(前面排了 8 兆的大件):**一半时间出错**(47%);
- 积压一大(64 兆):**几乎必然出错**(99.94%);
- 官方提供的三种"等一下"的栅栏(事件等待/事件同步/整条流同步):
  **全都等不到这次拷贝**——因为排队系统眼里这个工单已经"完成"了,
  没有东西可等。

最气人的是:**"没错"和"必错"之间只隔着一个偶然**。我们有一组配置
平时 0% 出错,一度以为它安全——把压力加到 64 兆,99.94%。**0% 不是安全,
是还没轮到你。**

## 四、为什么只有 NPU 上炸、GPU 上没事?

> ❌ **2026-08-28:本节前提作废**——两边同流语义**等价**(都有序且可见)。
> 引擎 bug(#14922)为真,但其平台层归因不成立,真凶候选见续集。原文保留如下。

同样的代码习惯(pinned 内存 + 异步拷贝 + 同一条流上接着算)在 CUDA 上是
教科书用法:CUDA 的流保证"前面的拷贝数据对后面的计算可见",这是白纸黑字
的语义。torch_npu 照抄了这套 API 的形状,但底下这条"最后一百米"没人修。
我们最初崩溃的那个引擎 bug(#14922),就是一张写着 -1 的旧便利贴被当成
新数据,送进了查词典的计算,一头撞出边界。

## 五、怎么办

- **立刻能用的安全写法**:拷贝时把 `non_blocking=True` 改成 `False`
  (同步拷贝)。我们的小数据只有 64 字节,同步的开销测不出来,线上已经
  这么修了(#14922)。✅ 此条至今有效,且被证明**跨机制稳健**。
- **给华为报 issue**(下一步):材料已经备齐——不是报"哪里错了",而是报
  "这层语义缺了一块,请告诉我们正确的异步用法是什么"。
  ❌ 2026-08-28:**issue 计划冻结**——没有层被证明存在可外报缺陷;
  已备材料归档,翻案后给 #14922 维护者补的是**更正评论**而非缺陷报告。
- **教训三条**:
  1. 测出 0% 错误不代表安全,可能是窗口没开;压力谱(从轻到重)才是体检;
  2. 监控本身会改变结果——我们一开性能档案,乱序就消失了(仪器把程序拖慢,
     货反而赶上了);
  3. "记录显示一切正常"和"数据真的到位"是两件事,**中间可能隔着一百米**。

## 续集(2026-08-28):第八次推翻,这次轮到终判本身

上面那个"最后一百米"的故事讲了两天,讲得连我们自己都信了。翻案从一步
看似平常的准备开始:

**我们决定给华为报 issue,按规矩先做一个零依赖的纯 CANN 复现**(绕开
torch,直接调最底层库)。它一跑就红——但这次我们多装了一个**阴性对照**:
同步拷贝模式,按定义不可能出错。结果它也红了。**仪器坏了,一切读数作废。**
这一下,过去两天的全部数据都要重新审。

拆仪器拆出来的真相,分四步:

1. **昇腾的提交管线是个约 2048 个任务的先进先出环**。host 可以领先设备
   一百到两百多步,塞满了才被反压限速。这不是缺陷,是设计——铁证是五种
   不同配置下"领先步数"全部精确等于 2048÷每步任务数,误差 ±1。
2. **我们的复现源是两页交替的便利贴**(每 2 步改写一次),而计数器
   **不分"旧值"和"未来值"**。host 领先两百步时,迟到的拷贝出发前,
   它要抄的那页早被后面的步改写了——送出去的是"未来值",计数器照单
   全收,记成了"读旧数据"。**"最后一百米"从始至终只存在于仪器里。**
3. **配对实验一锤定音**:同一个程序里加个开关——便利贴改成"每步一页、
   写完不改",全部配置立刻归零(包括 64 兆满压力);换回两页交替,
   99.85%/99.94% **分毫不差地回来**,方向清一色"未来值"。单变量,闭案。
4. **栅栏也平反了**:便利贴修好后重测,三种"等一下"全部正常工作。
   当年"0% 出错"的配置也恢复了清白——它在平台层**本来就是安全的**。

回头看,连当年"一开性能档案乱序就消失"的观察者效应都有了新读法:档案
把程序拖慢 → host 跑不到前面去了 → 便利贴来不及被改写 → 伪影消失。
它自始至终都在告诉我们"病根在 host 跑前",只是我们当时听不懂。

**那引擎的崩溃呢?** 案子还在,被告换人。引擎里那张"兜底便利贴"比复现
脚本更激进——**只有一页,每步都擦了重写**。新头号嫌疑:host 大幅跑前时,
迟到的拷贝抄到的是**后面"关门步"重新写上去的占位符 -1**,然后亲手把它
送上设备。这与三计数器的全部读数相容(包括唯一逃逸值恰为 -1),也解释了
CUDA 为什么不崩:那边 host 每步都被"等采样结果"拽着,跑不了那么远。
**判别实验当天跑完,定谳**:单页照崩(0/8),换"每步一页私有快照"全绿
(8/8,门照开 7 次、逃逸 0 个,单页时代 1 个 -1)——迟到的拷贝抄到了被
改写的单页,-1 是它亲手送上去的;顺序自始至终没人违反。全案闭合。

给下一班同事的教训清单,在原三条之外**换掉一条、加三条**:

- ~~"测出 0% 不代表安全"~~ → 保留但反转用法:**0% 也可能是仪器坏了**,
  阴性对照不绿,一切作废——这次救场的正是它;
- "监控会改变结果"→ 保留,并升级为破案线索:改变的是 **host 的步频**;
- ~~"记录正常 ≠ 数据到位"~~ → 撤销(平台层记录和数据一直是一致的);
- **计数器必须分方向**:读"旧值"和读"未来值"是两个相反的故事;
- **仪器也要做配对实验**:改一个变量,旧现象必须原样回来,否则是你把
  仪器改哑了;
- **深提交环是真实存在的产品行为**:host 写完 pinned 缓冲就改写它,
  是把"以为刚寄出"的数据亲手作废——这个坑与平台无关,谁都可能踩。
